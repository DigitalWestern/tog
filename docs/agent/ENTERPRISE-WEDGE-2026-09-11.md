# Enterprise wedge — measurement and sequencing (2026-09-11)

Status: **proposal**, written for the owner after the 2026-09-11 product
conversation ("sell to enterprises; the customs officer is the product").
Nothing here is committed to STATUS.md until the owner says so. Numbers in
§1 come from `tests/hitrate.py` runs on m6-fedora at the commit named there.

## 0. The one correction that shapes everything else

`--strict` is not "enterprise mode". It refuses **all fourteen** exception
kinds in `policy::KINDS`, and about half of them are not security findings:

| kind | what it means | security buyer cares? |
|---|---|---|
| `install-script-failed` | a lifecycle script failed under the sealed sandbox; the extracted package was kept | **yes** — unverified install state |
| `weak-integrity` | SHA-1 lock integrity accepted | **yes** |
| `unattested-mutable-state` | a writable projection was created without attesting its contents | **yes** |
| `unattested_index` | manifest named a private index / index-like option | **yes** (until WP3/WP5 make it configured) |
| `git-dependency` | dependency accepted without registry provenance | **yes** |
| `lock_disagreement` | lock digest does not match its manifest | **yes** |
| `artifact_not_provisioned` | an install-time download was skipped; fetched unverified at first use | **yes** |
| `unattested_cargo_lock` | Cargo.lock generated by the store cargo, not shipped | borderline |
| `artifact_provisioned` | blanket itself downloaded and verified an install-time artifact (TOFU) | no (this is the good case) |
| `built_from_source` | prebuilt binary compiled instead of downloaded | no (this is *more* trustworthy) |
| `file-collision` | two wheels shipped the same path | no |
| `requirement-skipped` | project-local / direct reference skipped | no |
| `skipped_optional` | optional group not requested | no |
| `toolchain-component-unavailable` | rust-toolchain component not pinned | no |

So there are **three numbers per repo**, all derivable from one permissive
run because the harness records every exception kind per repo:

1. **permissive ok** — the developer-experience number (today's headline).
2. **company-policy ok** — ok with no exception from the "yes" rows above.
   This is what a shipped `policy.toml` for companies would deny.
3. **strict ok** — ok with zero exceptions. The floor.

A literal `--strict` run (harness flag added 2026-09-11) exists to prove the
derivation, not because it carries new information: strict only adds
refusals, so every permissive miss is a strict miss and every clean
permissive ok is a strict ok.

Two things the fresh run taught that the 09-05 data could not:

- **Strict is dominated by `skipped_optional`** (1,104 records on Python

  should stop refusing it or it should stop being an exception kind; until

- **The hit-rate harness caught five npm regressions** that `cargo test`
  and `tests/acceptance.sh` did not (workspace-local packages, checked-in

  rows, one git-source checkout). Real repos are the only test of the
  projection code's contact with the filesystem. The harness needs to run
  before merges that touch npm projection or store directory checks.

## 2. What the numbers mean for the pitch

- The gap between permissive and strict is almost entirely
  `install-script-failed`. That is the *same* class the security buyer
  cares about most (scripts that download binaries at install time). Every
  fix there (declared-artifacts rows, `artifact_provisioned`) moves both
  numbers at once — it is the highest-leverage engineering on the list.
- `weak-integrity` on create-react-app is a lock-format artifact (npm v1
  locks with sha1). A company would rightly refuse it; the developer fix is
  "regenerate the lock", which blanket can say in one line.
- `file-collision` and `requirement-skipped` should never fail a company
  policy. If they stay in strict, strict is a worse enterprise number than
  the product deserves. Recommendation: ship a `company` policy template
  (the "yes" rows) and quote that number, not strict.

## 3. Sequencing — three layers, each a shippable claim

The prior conversation produced a list (Ubuntu, container mode, arm64,
fixed store path, close the `add` door, WP3, WP5). Ordering rule: **each
layer must make a sentence true that a buyer can verify.** Layers, with the
sentence each unlocks:

### Layer 0 — measure honestly (this week)

Sentence: *"Here is the hit rate, permissive and under company policy, on
the top 60 repos, on Linux, at this commit."*

- [x] harness `--strict` + `policy_denied` class (2026-09-11).
- [x] harness prints permissive / company-policy / strict itself
  (`COMPANY_DENY`, 2026-09-11).
- [ ] run the harness as a merge gate for npm-projection and store-check
  changes (five regressions slipped through between 09-06 and 09-10).
- [ ] fresh top-N pick alongside the pinned 60 (the pinned set is the
  trend line; the fresh pick guards against tuning to it).
- [ ] put Cargo, Go, Ruby, Elixir, .NET in the harness (manifest detection:
  Cargo.toml / go.mod / Gemfile / mix.exs / *.csproj). Until measured,
  "seven ecosystems" is a claim.
- [ ] HITRATE.md header rewritten to point at the latest run (it has been
  stale since 2026-09-05).

### Layer 1 — the customs officer never takes a break

Sentence: *"Nothing enters a blanket-managed project without passing
policy, and every entry is recorded."*

Doors open today (LIMITATIONS.md, `src/deps.rs` doctrine):

1. `add` / `remove` / `update` — the ecosystem tool runs unsandboxed with
   full network.
2. Missing-lockfile generation — same (`uv pip compile`,
   `npm install --package-lock-only`, `go mod tidy`, MSBuild restore).
3. `artifact_not_provisioned` — first use of a puppeteer-class package
   downloads unverified at runtime.
4. Elixir OTP relocation + runtime probe (two steps; touches staged object only).

Recommended mechanism, one design for doors 1–3: **blanket owns the
network path.** Run the delegated tool inside the existing sandbox with
`--unshare-net`, and hand it exactly one way out: a loopback/unix-socket
HTTP(S) proxy that blanket runs for the duration of the command. The proxy
(a) enforces the permitted-endpoint list, (b) logs every URL and digest
fetched into the closure as a `resolver-fetch` record, (c) is the natural
place private mirrors plug in later (WP3/WP5 map `pypi.org` →
`artifactory.corp`). bubblewrap cannot filter by host; a proxy can. This
needs its own design round and adversarial review before code; the
interesting failure modes are tools that ignore `HTTP_PROXY`, TLS
interception vs. CONNECT pass-through, and tools that shell out to git.

Cheaper first step that does not need the proxy: **`blanket audit`** — read
a project's closures and evaluate them against a named policy file without
rebuilding. Everything it needs is already recorded (exceptions per
closure; `strict_policy_rejects_cached_exceptions` proves policy can be
re-evaluated on recorded state). This is the CI admission gate command:
`blanket audit --policy company.toml` exits non-zero and prints the
offending kinds. About a day; no new trust boundary.

### Layer 2 — run where enterprises run

Sentence: *"It works in your CI and your agent sandbox, not just on a
Fedora workstation."*

- **Ubuntu/Debian verification.** Glibc floor is already declared;
  bubblewrap is packaged. Run `tests/acceptance.sh` on Ubuntu 24.04 and
  Debian 12. Expect one real wall: Ubuntu 24.04 ships
  `kernel.apparmor_restrict_unprivileged_userns=1`, which makes
  `bwrap --unshare-user` fail for unprivileged users unless an AppArmor
  profile allows it. That is the same class of failure as Docker's default
  seccomp profile refusing `CLONE_NEWUSER`.
- **"The container is the sandbox" mode.** Today `bwrap_preflight` is a
  hard `Unsupported` error with no fallback (`src/sandbox.rs`). Proposal: a
  machine-policy-only setting (never project, never env) that says the
  outer environment already denies network; blanket then runs the build
  with the same filesystem layout but without namespaces and records
  `sandbox = "external"` in the closure. Company policy can deny
  `external` sandboxes, so the record stays truthful and the knob cannot
  be used to weaken a laptop. This must be policy, not an env var —
  otherwise it is a "trust me" flag.
- **aarch64 Linux.** A pin-table row plus a wheel-tag band per ecosystem
  (LIMITATIONS.md says "not a port"). Graviton runners and Apple-hosted
  Linux sandboxes are arm64; every agent-sandbox vendor will ask.
- **Fixed store path.** blanket-notes.md already concluded
  `/opt/blanket/store` and deferred it because binary-cache sharing was
  post-MVP. Sandboxes are the demand that brings it back: a read-only
  store mounted into every container is the whole warm-start story.
  Near-irreversible; owner decision. Needs the GC guarantee's boundary
  stated for a shared mount (advisory `flock` on a bind mount is fine;
  on NFS it is not, and LIMITATIONS.md already says so).

### Layer 3 — the company layer (WP3 trust, WP5 policy, WP2 first)

Sentence: *"Your security team sets the rules once, per machine, and no
repo can loosen them."*

This is the archived plan's WP2 → WP3 → WP5 chain, unchanged. It is last
not because it is least important but because it is the most design-heavy
and Layers 1–2 are what let a technical infrastructure team adopt without
it. The proxy from Layer 1 is WP5's "enforcement must cover every door"
delivered early, and WP3's permitted-endpoint list is the proxy's config.

## 4. Decisions the owner has to make

1. **Ship a `company` policy template and quote that number** rather than
   strict. (Recommended: yes.)
2. **Registry-proxy design for the delegated-tool doors** — approve a design
   round, or pick a narrower fix (e.g. refuse `add` under company policy
   and require lock edits to happen outside blanket). The narrow fix keeps
   the door closed but makes the tool useless for the agent story.
3. **`/opt/blanket/store`** — decide now or explicitly defer again.
4. **First outside target**: a GitHub Action (`blanket sync --policy
   company && blanket sbom`) is the cheapest visible artifact and works on
   GitHub-hosted Ubuntu runners today if the userns wall is not hit; an
   agent-sandbox vendor needs Layer 2 first.

## 5. What to say to a security buyer (and what not to)

Say: acquisition and build happen behind one door; builds cannot reach the
network; every closure lists what went in and every exception that was
waved through; the SBOM is generated from that record, not from scanning a
blob.

Do not say: "malicious code cannot run." The sandbox bounds *acquisition
and build*. A hostile package can still put its payload in its build
output and run it at `blanket run` time with full network. Blanket's claim
is provenance and no-phone-home-during-build, not runtime containment.
The first meeting will ask; the answer should already be in the deck.
